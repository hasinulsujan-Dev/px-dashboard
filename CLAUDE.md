# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

PX Team Dashboard-2026 — a single-file static HTML/CSS/JS dashboard (no build step, no framework, no `package.json`) for Exabyting/bKash's "PX Team": Attendance tracking and a "Sailor's Report" misconduct/exception tracker. See `Docs/PRD.md` for the original product spec (note: its "Live Sync" section describing Google-Sheets-based Attendance sync is **stale** — Attendance now comes from a ZKTeco snapshot, see below — but the business rules and column layouts it describes are still accurate).

## Commands

There is no build/lint/test tooling. The workflow is: edit → sync → serve → verify in browser.

```bash
# Serve locally (already configured in .claude/launch.json, port 8934) — a thin wrapper
# around http.server that adds one endpoint, POST /api/sync-now (see below)
python3 serve.py 8934

# After ANY edit to px-dashboard.template.html, copy it to index.html
./sync-dashboard.sh

# Refresh the embedded Attendance snapshot from the ZKTeco BioTime API (all months)
python3 fetch-zkteco-snapshot.py                              # all months, Jan-Aug by default
python3 fetch-zkteco-snapshot.py --months January,February    # specific months
python3 fetch-zkteco-snapshot.py --env .env --out data.js     # explicit (also the defaults)
```

`fetch-zkteco-snapshot.py` needs `BIOTIME_BASE_URL` / `BIOTIME_USERNAME` / `BIOTIME_PASSWORD` in a root-level `.env` (gitignored, not committed). `serve.py` reads the same `.env` to serve `POST /api/sync-now`.

## Architecture

### Source-of-truth duplication — always sync

`px-dashboard.template.html` is the **only** file to hand-edit — it contains all markup, CSS, and JS inline. `index.html` is a byte-for-byte copy produced by `sync-dashboard.sh`; never edit `index.html` directly, changes will be lost. The one exception is `fetch-zkteco-snapshot.py`, which patches the `data.js?v=N` cache-busting query directly into *both* files after a fetch (see below) — everything else only ever touches the template.

### Two independent data pipelines, feeding one `DATA` object

`data.js` defines `const DATA = {months, employees, sailors, daily, profiles, sailorCriteria, sailorManual}`, loaded via `<script src="data.js?v=<timestamp>">`. The two report sections source their data completely differently:

- **Attendance** (`months`, `employees`, `daily`, `profiles`) is a **periodic snapshot** regenerated by `fetch-zkteco-snapshot.py` against the ZKTeco BioTime REST API (`/api-token-auth/`, `/personnel/api/employees/`, `/iclock/api/transactions/`). The browser itself can never call BioTime directly — it has no CORS support and the credentials live server-side in `.env` — so clicking the dashboard's "zkteco-api sync" button (`syncLiveRun()`) instead calls `POST /api/sync-now` on the local dev server (`serve.py`), which runs `fetch-zkteco-snapshot.py:sync_current_month()` to refetch *just the current month* live from BioTime and merge it into `data.js` (every other month is left untouched), then the browser reloads `data.js`. If `/api/sync-now` isn't reachable (e.g. the dashboard is opened as a static file, or `serve.py` isn't what's running), the click still falls back to reloading whatever `data.js` currently has, and says so in the toast. Run `fetch-zkteco-snapshot.py` directly (full month range) when you need to backfill or repair more than the current month.
- **Sailor's Report** (`sailors`, `sailorCriteria`, `sailorManual` keys in `data.js`) is **not synced from anywhere** — its criteria list and per-criterion entries are entered by hand in the Data Editor page ("Sailor's Raw — Manual Entries") and persisted to `OVR.sailorCriteria` / `OVR.sailorManualEntries` in `localStorage`. The `data.js` keys of the same name are legacy/unused leftovers from an earlier Google-Sheets sync and are not read anywhere in the client JS.

BioTime field mapping (`fetch-zkteco-snapshot.py`): `last_name → Employee ID`, `first_name → Name`, `nickname → Perks`, `department.dept_name → Department/Team`. `daily` rows are `[employeeId, "M/D", clockInMinutes|null, clockOutMinutes|null, status]`.

### Client-side calculation, not the fetch script, is what most pages read

`fetch-zkteco-snapshot.py` only pre-aggregates the coarse per-employee-per-month numbers (`att`, `wd`, `absent`, `late`, `b8`, `eco`, `avg`, `band`) stored in `employees`. Everything else — the Attendance Summary/Monthly tables, Sailor's Report computed criteria, the Month-to-Month Comparison matrix, Repeat Flags — is recomputed client-side in the template's `<script>` from `DATA` on every render, via:

- `buildMatrix()` / `MATRIX` — a `{roster, idx}` structure keyed by employee id and month, built from `DATA.employees` + `DATA.profiles`, refreshed via `refreshMatrix()`.
- `effRow(id, month)` — merges a `MATRIX` row with any manual override (`OVR.att[id+"@"+month]`).
- `isExcludedTeam(team)` — the single shared filter (prefix-matches `"Support Staff"` and `"Temporary"`, case-insensitive) applied everywhere teams are enumerated or aggregated; there is no other place that excludes these teams, so a new report/table must call it explicitly or it will silently include them.
- `isOnsite(e)` — `!/remote/i.test(perks + team)`, used by the Sailor's Report "Only onsite employees" criteria.

Business rules baked into both the fetch script and the client JS (keep them in sync if changed): weekday = not Friday/Saturday; Status = Late if clock-in > 10:00 AM (600 min) or a clock-out with no clock-in, On Time if clock-in ≤ 10:00 AM, Absent if neither punch exists; Early checkout = clock-out before 7:00 PM (19:00, 1140 min); employees are excluded from a month if `hire_date` is after that month's last day.

### Manual overrides and local state (`OVR`, `localStorage`)

`OVR` (`{att, sail, sailorCriteria, sailorManualEntries}`) holds all user-entered corrections/additions, persisted to `localStorage` via `save()`. It always takes precedence over synced/computed values (`effRow`, `getCriterionValues`). Sailor's Report criteria not auto-computed from Attendance are entered per month/criterion in the Data Editor page ("Sailor's Raw— Manual Entries"), backed by an employee-name `<datalist>` (`employeeNamesDatalist`, populated in `refreshMatrix()`) for fast lookup instead of typing full names.

### Sidebar / view routing

No router — every page is a `<section class="view" id="view-XXX">`, toggled visible via a shared `.on` class. Nav items are `.side-tab[data-v="XXX"]` buttons wired by a single generic click handler (`document.querySelectorAll(".side-tab").forEach(...)`) that flips both the tab's `.on` state and the matching `.view`'s `.on` state — adding a new page means adding a `.side-tab` with the right `data-v` plus a `.view` with the matching `view-` id, no other wiring needed. Pages nest under two collapsible sidebar groups ("Reports": Sailor's Report, PX Report; "Raw data": Attendance-Raw data, Sailor's Raw data, Data Editor), both closed by default, toggled via `toggleSideGroup(name)` acting on `#{name}Sub` / `#{name}GroupBtn`. **Do not give a group-toggle button the `.side-tab` class** — the generic handler above will silently overwrite its `onclick`.

`?year=2026` (default/active) vs `?year=2027` (a separate, largely empty stub page/shell for a future phase) is a real query-string switch, read once into the `YEAR` const at load.

### Known browser-cache gotcha

`<script src="data.js?v=N">`'s query string is the *only* thing that busts the browser's cache for `data.js` — the parent `index.html`'s own cache-busting is independent and does not propagate to it. `fetch-zkteco-snapshot.py`'s `bump_data_js_cache_version()` handles this automatically on every run (patches the `?v=` in both HTML files); if you ever hand-edit `data.js` directly, bump that query yourself or changes won't be visible after a normal reload.
